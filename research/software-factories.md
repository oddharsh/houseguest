# What houseguest takes from software factories

Houseguest is a software factory: a fixed line of phases, each run by its own agent, that turns an issue into a PR. Most factories in the literature work for a repo's own maintainers, so they can push, label, and merge. Houseguest works for a guest, so every step that reaches upstream waits for a person's yes. That one difference decides what transfers.

This page lists the sources, what each found, and where houseguest uses it, with the PR that brought each idea in. Numbers are from the sources as published; where secondary write-ups disagree, both are given.

## Sources and what they changed

| Source | What it found | Where houseguest uses it |
|---|---|---|
| [withastro/factory](https://github.com/withastro/factory) (Astro's triage and review factory) | Triage runs reproduce, diagnose, verify, and fix as separate subagents sharing one `report.md`. The author and reviewer personas loop with declines and a stand-still. An adversary writes a second fix from the base without seeing the PR. Advisory triage assumes a report isn't a vulnerability until shown | The phases as subagents and the blind intent check, stricter than Factory's verify step, which reads the report that assumes a bug (#1). `rounds.md` and the stand-still (#9). The second fix and the compare agent (#10). "Security reports" in recon (#8) |
| StrongDM's software factory ([Simon Willison's write-up](https://simonwillison.net/2026/Feb/7/software-factory/)) | End-to-end scenarios are kept outside the codebase, where the coding agents can't see them, like a holdout set. Success is the share of runs that satisfy the user | `holdout.md`: reports from the thread beyond the first are held out of the fix and run only by the final check (#14) |
| [Are "Solved Issues" in SWE-bench Really Solved Correctly?](https://arxiv.org/abs/2503.15223) (Wang, Pradel, Liu, ICSE 2026) | 29.6% of patches that passed SWE-bench's tests behaved differently from the developers' own fix; differential tests generated by PatchDiff exposed them | The compare agent's differential tests, and the final check's search for changes between base and HEAD that the PR doesn't mention (#15) |
| [Evaluating Agent-based Program Repair at Google](https://arxiv.org/abs/2501.07531) (Rondon et al., ICSE 2025) | Passerine produced a patch passing the bug's tests for 73% of machine-reported bugs but a correct one for 43%; for human-reported bugs, 25.6% and 17.9% (the ICSE version: 14.6% and 13.4%) | Why passing the new test isn't the last step: the final check reproduces the report itself (#5), and the second opinion exists (#10). Human-reported bugs, houseguest's whole domain, are where the gap is widest |
| AIDev studies of agent PRs on GitHub ([AIDev](https://arxiv.org/abs/2507.15003); [task-stratified](https://arxiv.org/abs/2602.08915); studies of unmerged PRs: [2602.00164](https://arxiv.org/abs/2602.00164), [2601.15195](https://www.emergentmind.com/papers/2601.15195)) | Over 456K agent PRs across 61K repos. Merge rates vary by agent (roughly 55% to 86%) against about 83% for humans in one sample. The commonest reasons a fix stays unmerged: failing tests, and another PR having fixed the issue first; larger diffs and unwanted features follow | `recheck.sh` before shipping (#11), red CI in `followup.sh` (#12), and the size and one-concern checks in `housecheck.sh` and `lean.md` |
| [Mutation-Guided LLM-based Test Generation at Meta](https://arxiv.org/abs/2501.12862) (FSE 2025) | ACH plants faults tied to a concern and writes tests that catch them; engineers accepted 73% of the tests. An LLM can flag faults that change nothing | `prove.sh` reverts each hunk of the fix alone to show the test notices, and tries the whole suite when it doesn't: a hunk nothing notices may change nothing (#3) |
| Cognition, "Don't Build Multi-Agents," and Anthropic's multi-agent research system ([LangChain's summary](https://blog.langchain.com/how-and-when-to-build-multi-agent-systems)) | Splitting agents loses the decisions hidden in each one's actions; parallel agents work when they mostly read. Reading parallelizes; writing doesn't | The judging agents (intent, review, compare, final check) stay isolated. The write phases log their decisions in `decisions.md` so a fresh run doesn't undo them (#14) |
| curl ends its bug bounty ([BleepingComputer](https://bleepingcomputer.com/news/security/curl-ending-bug-bounty-program-after-flood-of-ai-slop-reports/), January 2026) | AI-written reports flooded the program; one came with GDB sessions for a function curl doesn't have | `cites.sh` checks every file, line, function, and version a report cites before anyone reproduces it, including the user's own drafts (#13) |
| [addyosmani/factory](https://github.com/addyosmani/factory) (a reference factory for Claude Code and Codex) | Its gate script ends in a verdict line no agent may paraphrase, and a required check that can't run is `MISCONFIGURED`, exit 2, so a missing test command can't pass as green. Every skill must state what it dropped | `gather.sh` fails closed: a lookup that errors prints LOOKUP FAILED and exits 3, and a list that stopped at its limit says so. Turning it on surfaced a section that had always printed nothing, because `gh issue list` rejects the `authorAssociation` field and the error went to `/dev/null` |
| [vercel-labs/issue-graph](https://github.com/vercel-labs/issue-graph) | Traces an issue to the PRs that fixed it, their regressions, and open follow-ups before work starts, and reports its crawl limits and unknown counts instead of zeros | `gather.sh`'s "Work linked to" section: the issue's links, then whatever links to the merged fix PRs, marking what arrived after the fix merged. On vercel-labs/agent-browser#1113 it finds the regression (#1148) and the PR that removed part of the fix (#1173) |
| [asklokesh/loki-mode](https://github.com/asklokesh/loki-mode) | Every run ends in a receipt signed with a local Ed25519 key, and `loki verify` re-hashes it against the run's event log; the PR lists what was NOT PROVEN | `receipt.sh`: script-written verdicts are sealed, and the final check runs each repro through a hash-chained log the PR gate reads. HMAC with a local key instead of a signature, since only this machine's gate checks it. The PR body's limits sentence now comes from the ledger (move 6 in `pr-copy.md`) |
| Dan Shapiro, "The Five Levels" ([Simon Willison's summary](https://simonwillison.net/2026/Jan/28/the-five-levels/)) | Levels from autocomplete to a "dark factory" where no person reviews the code | Where houseguest sits on purpose: everything below the outward step can be automated, and the outward step can't. A guest who ships without reading what goes out under their name is the slop the rest of this page is about |

## What doesn't transfer

- **Maintainer powers.** Factory labels issues, pushes branches, and opens PRs on its own repo, and its personas can be assigned work. A guest can do none of that without being rude, so houseguest drafts and the user posts.
- **Running as a service.** Factory is a webhook-driven Worker with durable coordinators; StrongDM builds digital twins of the services it calls. Houseguest runs in one person's session, against a repo it's visiting once.
- **The older meaning.** Cusumano's *Japan's Software Factories* (1991) and Greenfield and Short's *Software Factories* (2004) are about reuse and product lines inside one organization. The word is the same; the problem isn't.
